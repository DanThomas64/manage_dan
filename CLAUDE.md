# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
cargo build                    # Debug build
cargo build --release          # Release build
cargo build -p <crate>         # Build specific crate
cargo check                    # Type-check without building
cargo test                     # Run all tests
cargo test -p <crate>          # Test specific crate
cargo test <test_name>         # Run a single test by name
cargo clippy                   # Lint
cargo fmt                      # Format code
cargo fmt -- --check           # Check formatting only
cargo run -p app                # Run the backend server (http://0.0.0.0:8080)
cargo run -p tui                # Run the TUI (needs the server running; reads MANAGE_API_URL, default http://127.0.0.1:8080)
./deploy.sh                     # Build release + install as a native systemd service + nginx reverse proxy
./deploy-frontend.sh            # Copy frontend/index.html to the nginx static path only — no build, no service restart
./scripts/dev/run_scratch_instance.sh [port] [notebook]  # Run a second, isolated app instance (own port/db/nb notebook) alongside the real deployed one
./scripts/dev/clean_test_pollution.py [--apply]          # Find (dry-run) / remove (--apply) test data that leaked into real nb notebooks
./scripts/dev/demo_journal.sh [restore]                  # Swap the live hledger journal for a canned demo one (backing up the live one first); `restore` puts the live one back
```

**Test isolation**: `nb` notebooks are global (not scoped by cwd), so an integration test isolates itself two ways — a scratch `std::env::temp_dir()` cwd (keeps `app.sqlite`/`printed_tasks` separate) *and* a uniquely-named `zz_`-prefixed notebook for whatever it's directly creating (keeps that data out of real notebooks). Neither of those isolates a side effect that targets a different, hardcoded notebook regardless of which notebook the test itself used — the one existing example is `todo::complete_item`'s `log_completion`, which always logs to the shared `log` notebook. `todo/tests/nb_backend.rs`'s `nb_backend_end_to_end` used to skip this and, for a long time, silently wrote a real "Completed: Integration test todo" entry into the real, live daily log on every `cargo test` run — cleaned up via `clean_test_pollution.py --apply` and fixed by giving it the same full `NB_DIR` swap `todo/tests/completion_log.rs` already used (see that test's own doc comment for the "why" of `NB_DIR` over a scratch notebook name alone). Going forward: any test whose actions could reach a shared/hardcoded notebook this way should (a) prefer `NB_DIR` isolation when practical, matching `completion_log.rs`, and (b) regardless, give its own test data a title starting with `zz_test:` or a `zz-test-data` tag, so `clean_test_pollution.py` (or a quick grep) can find and remove it even if isolation is ever incomplete or bypassed.

Local config lives in `config/local.toml` (gitignored, layered over `config/default.toml`); any setting can also be overridden via an `APP_`-prefixed env var — a top-level field is `APP_<FIELD>` (e.g. `APP_API_PORT=8099`), but a field nested under a `[section]` needs a **double** underscore between section and field (`APP_<SECTION>__<FIELD>`, e.g. `APP_PRINTER__MODE=usb`, `APP_TODO__NB_NOTEBOOK=work`) — `app/src/config.rs`'s `Environment` source uses `"__"` as the nesting separator specifically because most field names (`nb_notebook`, `api_port`, `monitor_interval_secs`, ...) already contain a literal underscore, which a single-underscore separator can't tell apart from nesting (it doesn't error, it silently no-ops — confirmed via a regression test, `env_var_override_works_for_underscored_field_names`, added after this was discovered). `api_port` (default 8080) is what makes `run_scratch_instance.sh` possible — a scratch instance's `local.toml`/`APP_API_PORT` gives it its own port so it can run concurrently with the live deployment without a bind conflict; the notebook name is what actually keeps it off real todo data (nb notebooks are global, not scoped by cwd).

Each crate versions independently — every crate's own `Cargo.toml` sets its own `version`, there is no shared workspace version. Bump only the version(s) of the crate(s) whose code actually changed in a given PR.

## Architecture

This is a Rust Cargo workspace with one binary (`app`) and library crates: `db`, `log`, `printer`, `todo`, `lists`, `notes`, `project`, plus a second binary `tui`. The `app` crate depends on all library crates. `frontend/` (vanilla JS SPA, served by nginx) and `android/` are separate, non-Cargo clients of the HTTP API.

**Execution flow**: `main()` (`app/src/main.rs`) loads `AppConfig`, calls `SystemsStatus::init()` (`app/src/nogo.rs`) which sequentially calls `init()` on each subsystem crate in dependency order (db → log → notes → project → printer → todo → lists), tracking per-subsystem `Status` (Go/Nogo/Degraded/Unknown/Init). DB is initialized first so the log table exists before logging starts. `notes::init()` checks for the `nb` CLI binary; the notes subsystem goes Nogo if `nb` is not installed. `SystemsGoNogo::calculate_initial_status()` derives overall health from the fold of all subsystem statuses; `start_monitoring()` spawns a tokio task that recomputes it every 500ms. After init, the app prints a startup receipt to the configured printer (todo/list stats fetched concurrently via `tokio::join!`, with failures rendered as placeholder text rather than aborting startup), spawns background tasks (print monitor, daily summary, end-of-day completed summary — each printed once immediately if not already run today, then rescheduled to their configured hour), then starts the `warp` HTTP API server (`app/src/api.rs`) at `/api/v1/...`.

**Standardized module pattern** — every library crate follows the same structure:
- `lib.rs`: `init() -> Result<(), Error>` and tests
- `{crate}_error.rs`: custom error type via `thiserror`
- `{crate}_prelude.rs`: re-exports for ergonomic imports

`app/src/error.rs` defines `AppError`, which wraps every subsystem's error type (`#[from] DbLibError`, `NotesLibError`, etc.) via `thiserror`'s `#[error(transparent)]`, so subsystem errors surface at the top level without manual conversion.

Every library crate `app` depends on (`db`, `log`, `notes`, `project`, `printer`, `todo`, `lists`, `finances`) also exports `pub const VERSION: &str = env!("CARGO_PKG_VERSION")` from its `lib.rs` — `env!` expands at compile time using *that* crate's own Cargo.toml (each crate versions independently, see above), not whichever crate happens to read the const, so `app/src/api.rs`'s `GET /api/v1/version` handler can aggregate all of them (plus its own `env!("CARGO_PKG_VERSION")`) into one response without any of them needing to know about each other. `tui` is deliberately not included — it's a sibling binary the server has no dependency edge to, not a library `app` links against, so there's no equivalent `tui::VERSION` for `app` to read; the TUI's own screens already show its own version directly (see below) since it *is* `tui`'s own crate.

**Shared workspace dependencies** (declared in root `Cargo.toml`, inherited with `workspace = true`): `tokio` (full, async runtime), `tracing` (structured logging), `thiserror` (custom errors), `anyhow` (error context), `chrono` (date/time), `serde`, `config` (layered TOML + env config), `escpos` (thermal printer), `reqwest` (HTTP client, used by `tui`), `uuid` (currently unused by any crate).

**Logging**: `tracing-subscriber` configured in `app/src/main.rs` with RFC 3339 timestamps, line numbers, ANSI disabled, DEBUG level.

**`db` connection & local read cache**: `db::execute_async` (and `log_event`) share one lazily-opened `tokio_rusqlite::Connection`, held in a `tokio::sync::OnceCell` (`db::get_connection()`) rather than opening a fresh connection (and OS thread) per call; `db::init()` sets `PRAGMA journal_mode=WAL` so the background sync monitors' writes don't block API reads. Besides the pre-existing bookkeeping tables (`printed_tasks`, `todo_nb_index`, etc.), `db` also holds a local read-through cache mirroring `nb`-backed content that would otherwise require a live subprocess round trip on every list read: `todo_cache` (one row per todo, `labels`/`subtasks`/`reminders` as JSON `TEXT` columns, indexed on `project_title`) and `note_cache` + `note_cache_tags` (the latter a normalized per-tag table, not a JSON blob, so `db::note_cache_get_by_tag` is an indexed join rather than a scan). `note_cache` deliberately stores only a truncated `preview` (first 300 chars) rather than a note's full `content` — list/browse views never render more than that; opening a single note and full-text `search()` still go live. `nb` remains the source of truth for both; the cache exists purely to make list/browse/project-scoped reads fast. It's kept fresh two ways: synchronously, by the write-path dispatchers (`todo::create_item`/`update_item`/`complete_item`/`delete_item`/`archive_item`, `notes::create`/`update`/`delete`) upserting/deleting the corresponding cache row immediately after a successful backend write; and periodically, by a background sync pass (`todo::monitor::run` and the analogous `notes::monitor::run`, both spawned in `app/src/main.rs` on `AppConfig::get().monitor_interval_secs`, default 30s) that reconciles the cache against the live `nb` notebooks and removes rows for anything deleted externally (e.g. edited directly via the raw `nb` CLI, bypassing the app). The sync pass (`todo::backends::nb::sync_cache`, `notes::sync_cache`) skips re-reading/re-parsing any item whose source file's mtime (stat'd locally, not another subprocess call) hasn't changed since it was last cached, stored in each row's `source_mtime` column — so a sync pass's cost scales with how much changed, not with total item count. This introduces an accepted eventual-consistency window (up to one sync interval) for edits made outside the app, or if the process crashes between a write and its cache upsert — `POST /api/v1/todo/resync` / `POST /api/v1/notes/resync` (and the "↻ Refresh" entry in the frontend's Notes/Todo "☰" menu) force an immediate sync pass rather than waiting it out. `todo::read_items()` and `notes::list()`/`tags()` read the cache directly; `todo::read_items_by_project`/`notes::list_by_tag` are the indexed project-scoped equivalents the `project` crate uses (see below).

**Todo subsystem**: todos are stored as files in an `nb` notebook (`todo/src/backends/nb.rs`, dispatched from `todo::create_item`/`read_items`/etc. in `todo/src/lib.rs`; name set by `todo.nb_notebook` in config, default `"todo"`) — the same `nb` CLI the notes subsystem shells out to, with priority encoded as a `<!-- priority: N -->` HTML-comment header since `nb` has no native priority field. Priority is 0–5 (0=Unset, 1=Low, 2=Medium, 3=High, 4=Urgent, 5=Do Now) — both clients (TUI, frontend) clamp/validate to this range. `read_items()`/single-item reads are cache-backed (see above); every write dispatcher re-syncs the affected row(s) itself, and bulk operations that don't return which items changed (`archive_project_todos`/`restore_project_todos`) trigger a full `sync_cache()` afterward rather than tracking individual ids. `todo::backends::nb::hydrate_item` reads a todo's content from its already-resolved local file path (from `list_paths_in_folder`'s `--paths` output) instead of shelling out to `nb ...:show` a second time — confirmed byte-identical for real items with Description/Tasks/Tags/Due sections populated. New todos are printed once on creation (`print_ticket_on_creation`) and, independently, by the background print monitor (`todo/src/monitor.rs`) whenever it sees changed content — this same loop now also runs the cache-sync pass immediately before each print-check poll, since `poll()` reads via `crate::read_items()`, which is cache-backed; because creating a todo shells out to `nb` multiple times, which can take long enough for the monitor's own poll to observe the same brand-new item first, both paths claim the print atomically via `db::printed_claim` (an `INSERT ... ON CONFLICT ... WHERE` that only one caller can win) before printing, rolling the claim back on print failure so the monitor retries next poll. Marking a todo *completed* (not un-completing one, and not re-completing an already-completed one — `complete_item` fetches the item first to check its prior state) also logs a daily-log entry via `notes::create_log` (`todo::log_completion`), tagged `todo-complete` and, if the todo belongs to a project, also `project-<slug>`; this is best-effort (a logging failure only warns, it doesn't fail the completion), since the `log` notebook is a `notes`-crate concept independent of the todo subsystem itself.

**QR ticket page** (`GET /todo/:id`, `app/src/api.rs`'s `get_todo_page_handler`): the page a printed ticket's QR code (`manage-dan://todo/<id>`, see `PrintJob::with_qr` in `todo::print_ticket`) opens to — a single self-contained HTML/CSS/JS blob embedded as a Rust format string, not part of the `frontend/` SPA. It fetches `GET /api/v1/todo/:id`, renders title/project/due/priority/labels/description/subtasks/reminders/history read-only, and has a "Mark Complete" button. It also has an "Edit Task" button that swaps a `#view-mode`/`#edit-mode` toggle (`toggleEdit()`) to an inline form (title/description/due date+time/priority/labels/subtasks — mirrors the frontend's own Todo edit form fields, minus project reassignment) and `PUT`s the full `TodoItem` back to `/api/v1/todo/:id`, preserving `completed`/`created_at`/`completed_at`/`printed_at`/`archived`/`reminders`/`project_title` from the currently-loaded item, same convention `frontend/index.html`'s `submitTodo()` uses. `render(t)` clears every dynamic container's `innerHTML` (and resets card `display`/button state) before repopulating, rather than only ever running once — needed so a post-save `load()` re-render doesn't duplicate the badges/subtasks/history rows that `render()` previously only ever appended to once per page load. `GET /api/v1/todo/:id`'s route (`get_one` in `todo_routes()`) has to be listed in the `.or()` chain against a `read_all` filter that itself requires `warp::path::end()` — without it, `read_all` (`todo_base.and(warp::get())`, no further path constraint) matches *any* `GET /api/v1/todo...` path first (warp's `.or()` takes the first filter that matches, not the most specific one), silently serving the full array back to a single-item request; every consumer of that shape (the QR page above) then reads `undefined` off an array for every field, which is why routes throughout `lists_routes()`/`notes_routes()` always pair a bare path segment filter with an explicit `path::end()` before `.or()`-ing alternatives — `todo_routes()`'s `read_all` was the one place this had been missed.

**Other QR-linked pages**: two more standalone pages exist alongside the todo one, all three sharing the same amber "Dispatch Ticket" `:root` custom properties/dashed-border/mono-uppercase-badge conventions as `frontend/index.html` (duplicated per-page rather than shared, since each is a single self-contained HTML string, not part of the SPA) — `GET /notes/:id?notebook=&folder=` (`get_note_page_handler`, a markdown viewer via `marked.js` with title/tags/content `view-mode`/`edit-mode` editing that `PUT`s back to `GET /api/v1/notes/:id?notebook=&folder=`, mirroring `frontend/index.html`'s own `notesSaveEdit()` payload shape; `folder` addresses a note inside a notebook subfolder, see "Notes tree / subfolders" above) and `GET /list/:id` (`get_list_page_handler` — a shopping-list viewer with tap-to-check items via `PATCH /api/v1/lists/items/:id/check`, plus an always-visible "Add Item" form that `POST`s to `GET /api/v1/lists/categories/:id/items`, backed by a new `lists::get_category(id)` and `GET /api/v1/lists/categories/:id`). All three pages' "back"/"dashboard" action is `window.location.href='/'`, not `history.back()` — a page opened fresh from a QR scan has no browser history to go back to. `lists::print_list` now also calls `.with_qr(format!("manage-dan://list/{}", category_id))`, matching the pattern `todo::print_ticket`/`notes::print` already used — previously lists printed with no QR at all. The notes QR (`manage-dan://notes/{nb_id}?notebook={notebook}`) had silently never worked: it used to encode `{notebook}:{nb_id}` as one opaque path segment (a leftover from before notes had numeric per-notebook ids), which the real route's `u64` id parser rejects outright — fixed to match the query-string shape the HTTP route actually expects, with the Android side (`MainActivity.kt`'s `deepLinkUrl()`) updated to match. Android's manifest also gained a third `manage-dan://list/*` intent-filter alongside the existing `todo`/`notes` ones. Separately, `deploy.sh`'s nginx config only proxied `/api/` and `/todo/` to the app — `/notes/` (pre-existing) and `/list/` (new) were never reachable through the real deployed nginx front door at all (silently falling through to the SPA's `index.html` instead), only via direct `:8080` access; both are now proxied the same way `/todo/` is.

**Emoji stripping on print**: `printer::PrintJob::new(origin, title, lines)` strips emoji from all three arguments before storing them (`printer::strip_emoji`/`is_emoji`), rather than at each call site — this is the one place every ticket (todo, note, list, daily/weekly/completed summaries) funnels through regardless of which crate built it, so it covers both user-typed content (a note/task/list-item's own text) and this app's own ticket-formatting strings uniformly. `is_emoji` is deliberately narrower than "any non-ASCII character": it only matches the common emoji Unicode blocks (pictographs, emoticons, transport, misc symbols U+2600-U+26FF, dingbats U+2700-U+27BF, regional indicators, variation selectors, the ZWJ used to build compound emoji) — box-drawing (`─`), bullets (`•`), em dashes, and accented Latin all fall outside those ranges and print fine, so existing ticket-formatting characters (e.g. `notes::print`'s `─` separator and `•`-joined tag line) are untouched.

**Notes subsystem**: notes are not stored in the app's own DB (aside from the read cache described above) — the source of truth is markdown files managed by the external [`nb`](https://xwmx.github.io/nb/) CLI, with full-text search shelled out to `nb search` (the one read path deliberately left off the cache — see below). If files are edited outside `nb`, its index must be resynced with `nb index reconcile`. `nb_client.rs` always addresses notebooks with an explicit `notebook:cmd` prefix, including `home` — `nb` persists whichever notebook a colon-prefixed command last targeted as its own "current" notebook, so a bare/unprefixed command silently drifts onto that instead of `home`. Listing (`nb_list`) and tag aggregation (`nb_tags`) use `nb_list_paths` — one `<notebook>:list --paths` call per folder in the notebook (root included, walked recursively — see "Notes tree / subfolders" below), resolving every note's file path in that same call — and parse each file locally (`parse_note_file`), rather than a separate `nb show --path` subprocess per note; its line parser (`parse_list_path_line`) takes the whole trimmed remainder after `[id]` as the path rather than splitting on whitespace, since a `--paths` line is exactly `[id] <path>` with nothing else following it, and a moved/restored note's filename can itself contain a literal space (see the project subsystem's `nb move` note below) that a whitespace split would truncate; `nb_search` doesn't get the same treatment (`nb search --all --path` returns bare paths uncorrelated with ids, confirmed) so full-text search still pays a per-result `nb_show`, deliberately left as-is since result counts are typically small. Two distinct notebook-exclusion sets exist in `notes/src/lib.rs`: `EXCLUDED_FROM_ALL` (`log`, `todo`, `archive` — never shown in an unscoped "All" listing, applied in Rust after a cache read) vs. the narrower `EXCLUDED_FROM_CACHE` (just `log`, `todo` — nothing ever reads those back out of `note_cache`, since the daily-log view has its own always-live path and todos live in `todo_cache`); `archive` and every per-project notebook *are* cached, since each is still reachable via a scoped fetch (the "☰ → Archive" browse, and project-note scoping) even though neither appears in "All".

**Notes tree / subfolders**: every note also carries a `folder` field — the path of the subfolder it lives in within its notebook (e.g. `"Projects/Sub"`), empty for a notebook's root — surfaced in the frontend's Notes → Browse panel as a file-manager-style tree (folder rows to drill into, a breadcrumb to climb back out, only active while one specific notebook is selected — the "All" pill stays the old flat cross-notebook list) with a "Move" action on the note viewer and a "New Folder" entry in the view-options menu. This exists because `nb` numbers items *per listing scope*, not per notebook — a note at a notebook's root and a note inside one of its subfolders can both be "id 1" at the same time (confirmed against a real `nb` install), so once folders are in play a bare `(notebook, nb_id)` pair no longer uniquely identifies a note; `folder` had to become part of that identity everywhere: `note_cache`/`note_cache_tags`'s primary keys (`db::init` rebuilds both tables in place — SQLite can't `ALTER TABLE` a PK — the first time it sees the old, folder-less schema, treating every pre-existing row as root-level since it must predate folders), every `notes` crate function that addresses a single note (`get`/`update`/`delete`/`print`/`archive_note`), and the `notebook=`/`folder=` query-param pair every corresponding `/api/v1/notes/...` route now takes (a request lacking `folder` defaults to `""`, i.e. root, matching pre-folder behavior). `nb_client::nb_list_paths` walks a notebook's whole subfolder tree recursively (one `nb list <folder>/ --paths` call per folder — folders show up as their own `📂`-marked entries rather than having their contents inlined, so there's no cheaper single call) and returns both every note found (with its folder) and every folder path visited, including empty ones; `notes::sync_cache` and the new live-walk `notes::list_folders` (backing `GET /api/v1/notes/folder-tree?notebook=`, distinct from the pre-existing and confusingly-named `GET /api/v1/notes/folders`, which actually lists *notebooks*) both build on it. Moving a note (`notes::move_note`, `PATCH /api/v1/notes/:id/move?notebook=&folder=`, body `{dest_folder}`) re-numbers it in the destination scope — `nb_client::nb_move` now parses the moved-to id/folder back out of `nb`'s own "Moved to: [notebook:folder/id]" output (the same bracket-parsing convention `nb_add` already used for "Added:") and returns it, rather than assuming the id survives the move, since it usually doesn't; every caller (the API handler, `notes::archive_note`'s project-archiving path, which now also addresses its source note by folder instead of assuming root) treats the response as the note's new identity. `notes::create_folder`/`POST /api/v1/notes/folders` (`nb <notebook>:add folder <path>`) creates a (possibly nested) subfolder ahead of moving anything into it.

`notes::sync_cache`'s per-notebook reconciliation loop only ever visits notebooks that still exist (`nb_client::nb_notebooks()`'s current live listing) — a notebook deleted outright (a raw `nb notebooks delete`, or, historically, an ad hoc test/scratch notebook created directly via `nb` rather than through the project subsystem, which does clean up its own notebook on permanent delete) is simply absent from that listing and so never gets reconciled, leaving its `note_cache` rows orphaned forever instead of pruned — they'd keep showing up in "All"/search indefinitely, pointing at notes that no longer exist anywhere. Fixed with one extra pass after the main loop: every notebook name still present across *all* cached rows (`db::note_cache_get_keys(None)`) that isn't in the current live notebook set gets its rows dropped too, regardless of which notebook. (A batch of these had already accumulated live from exactly this — ad hoc `nb notebooks add`/`delete` cycles during manual testing of the folder-tree feature above — and were purged by hand once the fix was written, the same one-off cleanup `scripts/dev/clean_test_pollution.py` already automates for a different, tag/title-based pollution pattern; that script doesn't cover this whole-notebook case, since it only looks for `zz_test:`-prefixed titles/tags, not gone-entirely notebooks.)

**Log feature**: a dedicated `log` notebook, driven by `nb daily`, backs `POST`/`GET /api/v1/notes/daily`. Each entry is appended to that day's file under an auto-generated `## HH:MM:SS` heading, body-formatted with the same title/tags/content layout regular notes use (`nb_client::format_note_body`). `notes::recent_logs()`/`recent_logs_tagged()` (`nb_client::nb_daily_entries`) list every daily-log file's path in one `--paths` call, then filter to the requested `days` window by each file's own filename-derived date *before* reading any file — so cost scales with how many days are actually requested, not with how many daily-log files have ever been written; deliberately left off the `note_cache` read-through cache described above (already bounded, so the marginal benefit was judged too small to justify caching on top). The `log` notebook is excluded from the general notes browsing surfaces (`folders`/`list`/`search`) so daily-log files don't clutter regular note browsing.

**Project subsystem** (`project` crate, `/api/v1/project...`): lets todos/notes/log-entries/lists be grouped under a named project, without changing how anything behaves when created *without* one — association is purely additive (a shared tag/folder/list-group), not a new storage layer. `project::init(base_dir)` (config: `[project] base_dir`, default `~/projects`, `~` expanded manually) creates the `projects` table (`id`, `name`, `slug`, `tag`, `list_group_id`, `fs_path`, `archived_at`, `created_at`); `create_project(name)` derives a snake_case `slug` (words joined with `_`, not `-`), creates a dedicated `lists` group (same name) with a default "General" category, an nb notebook named `slug`, a filesystem folder under `base_dir`, and a `project-<slug>` tag (the `"project-"` prefix itself stays hyphenated — it's a fixed literal, not slug-derived). Scoping reuses existing mechanisms unmodified: the `nb` todo backend already maps `TodoItem.project_title` 1:1 onto an nb subfolder (`todo/src/backends/nb.rs`), so project todos are created with `project_title = Some(slug)` and read back via `todo::read_items_by_project(slug)` — an indexed `todo_cache` query (see the local read cache above), not a fetch-everything-then-filter-in-Rust scan; notes are tagged `project-<slug>` and read back via `notes::list_by_tag(tag)`, the equivalent indexed `note_cache_tags` join; log entries are tagged the same way but read via `notes::recent_logs_tagged`, which stays on its own live (but already-bounded) path rather than the cache; lists are just the project's own group, fetched via `lists::list_categories(list_group_id)`. `project_detail(id)` aggregates all four via `tokio::join!`, with each fetch best-effort (a subsystem being down blanks out just its own section, not the whole page). Deleting a project archives it, never destroys data: tagged notes and nb todo files are moved (`nb move`, which requires the destination notebook to already exist — `notes::ensure_archive_notebook()` bootstraps the shared `archive` notebook first) into `archive:<slug>/...` and `archive:<slug>/todo/` (trailing slash required, or a second todo silently overwrites the first), the project's filesystem folder is zipped (`zip` CLI) to `<base_dir>/.archive/<slug>.zip` and the live folder removed, and `archived_at` is set — the `projects` row and its `lists` group are never deleted. Every `nb move`/`rename` call in this codebase (`notes::nb_client::nb_move`/`nb_restore_folder`, `todo::backends::nb::archive_project_todos`/`restore_project_todos`) invokes it as `<notebook>:move` (the notebook-prefixed subcommand itself), never bare `move` plus a separate `notebook:id` source selector — the installed `nb` CLI's own top-level argument dispatcher mishandles the latter shape specifically for `move`/`rename`, hitting an internal "Not found" error before ever reaching the actual file move, confirmed via a minimal repro against a real `nb` install; the notebook-prefixed form sidesteps the bug entirely and is otherwise equivalent. Archiving notes only clears the note's stale old-location cache row per note (`notes::archive_note`); `project::archive_project` does one `notes::sync_cache()` call after the whole tagged-notes loop rather than per note, and `notes::restore_archived_notes` does the same once after its bulk move — both mirror `todo::archive_project_todos`/`restore_project_todos`'s existing post-bulk-move `sync_cache()` pattern, so a project's restored/archived notes are visible immediately rather than only after the next background monitor interval. Log entries tagged with the project are deliberately left untouched in the shared `log` notebook (no per-entry removal is possible; daily-log files pack many entries into one shared per-day file).

`restore_project(id)` reverses `archive_project`: notes are nested one level deep at `archive:<slug>/` once archived (`nb`'s own root-level listing doesn't descend into subfolders, and a folder-nested item is addressed as `folder/id`, not a bare id — `notes::restore_archived_notes` parses the folder-scoped listing and moves each note back to the project's own notebook root in one pass rather than going through the bare-id-only `nb_show`/`nb_move` path), todos are moved back by folder (`todo::restore_project_todos`), and the zip is unzipped back into place (`unzip -o -d <base_dir>`) and removed. `delete_project(id)` permanently destroys an already-archived project — refuses on a live (non-archived) one — by deleting the whole `archive:<slug>/` folder in one call (recursively removes the nested `archive:<slug>/todo/` too), the project's own now-empty notebook, the archive zip, the `lists` group, and finally the `projects` row itself (in that order — the row must go *before* the group, since `list_group_id` is a foreign key into it). Both endpoints are exposed as `POST /api/v1/project/:id/restore` and `DELETE /api/v1/project/:id`. The archived-project detail view exposes both: the frontend's `renderArchivedProjectDetail` gets "Restore"/"Delete Permanently" buttons (the latter behind a `confirm()`, navigating back to the project list on success), and the TUI mirrors them on the Project screen as `u` (restore) and `D` (permanent delete, behind a `y`-to-confirm prompt).

**Project favourites + Home tiles**: `projects` also carries `favourite` (bool, default `0`) and `icon` (`Option<String>`, a single emoji, `NULL` by default — both added via best-effort `ALTER TABLE ... ADD COLUMN` migrations in `project::init`, since plain non-PK columns don't need the note-tree feature's table-rebuild treatment) — `project::set_favourite(id, bool)`/`set_icon(id, Option<&str>)` (`PATCH /api/v1/project/:id/favourite` / `/icon`) toggle them independently. `set_icon` caps the input at 8 chars rather than validating it's really a single emoji (proper grapheme-cluster-aware validation is more than this is worth), generous enough for multi-codepoint compound emoji (ZWJ sequences, skin-tone modifiers) while still bounding storage; the frontend also HTML-escapes the icon on every render (`esc()`), since it's free-text stored as-is, not restricted to emoji server-side. Favouriting a project surfaces it as an extra Home-page tile (`renderHomeFavourites()`, `#home-favourite-tiles`, a `display:contents` wrapper so injected tiles participate directly in the existing `.home-tiles` flex row) showing its `icon` (default 📁) and name, linking straight to Project Detail — rendered on initial page load, and refetched (not cache-gated by `ensureProjectsLoaded`'s `projectsLoaded` flag, since Home is the landing page and freshness matters more here) every time `showView('home')` runs. Both the Projects-list card (a `★`/`☆` corner toggle plus a clickable leading icon, `toggleProjectFavourite`/`editProjectIcon`) and the Project Detail "☰" menu (`pdToggleFavourite`/`pdEditIcon`, mirroring the existing Archive entry there) can flip either setting; `syncCurrentProjectMeta()` keeps `currentProjectMeta` (the Detail menu's own copy of the project row — tracked separately from `currentProjectDetail`, which only holds the live aggregated todos/notes/logs/lists payload and is never populated for an archived project) in sync regardless of which surface made the change.

**Finances subsystem** (`finances` crate, `/api/v1/finances/...`): backed by the external [`hledger`](https://hledger.org/) CLI rather than the app's own SQLite database — a plain-text double-entry journal file (`[finances] journal_path` in config, default `data/finances.journal`) is the source of truth, the same division of labour the `notes` subsystem uses for `nb`-managed markdown (`finances::journal_writer` formats/appends journal text, `finances::journal_parser` reads periodic-rule/`account`-directive blocks back out, `finances::hledger_client` shells out for balance/forecast queries). `finances::init()` (called at startup from `nogo.rs`, after confirming `hledger` is on `PATH`) creates the journal's parent dir and, if the journal file doesn't exist at all yet (a brand-new deployment, not an existing-but-empty file — the latter is left untouched, since a user may have deliberately cleared it), seeds it with one default "Checking" asset account directive rather than leaving it completely empty, so spending/recurring entries have somewhere to post against immediately instead of erroring until someone thinks to add an account by hand. Four concepts: `SpendingEntry` (one-off dated transactions tagged `stupid`/`survival`), `RecurringItem` (hledger periodic rules, `~ <period>  ; id:... name:...`, one of Weekly/Biweekly/Monthly/Yearly), `Account` (a named `assets:`/`liabilities:` account, registered via a bare `account <path>  ; id:... name:...` directive line rather than a transaction, so it can appear in dropdowns with a $0 balance before anything's posted against it), and `TransferEntry`/`RecurringTransfer` (a movement between two of the user's own accounts — see below). A `RecurringItem` can carry an optional `reference_date`, embedded into the period expression as hledger's own `from <date>` anchor clause (`models::build_period_phrase`/`parse_period_phrase`) — this actually changes hledger's forecast math (e.g. which week a biweekly item lands on), not just cosmetic metadata. Every `SpendingEntry`/`RecurringItem` now also carries an `account` (the hledger path of whichever `Account` it posts against) instead of a hardcoded `assets:checking`; `finances::journal_parser::parse_block`'s income/expense split is generalized to key off which leg is `expenses:`/`income:`-prefixed, not off the other leg's prefix, so it works uniformly whether that other leg is an asset or a liability account (a credit card). "Quickly update the current balance" (`finances::set_account_balance`, `PATCH /api/v1/finances/accounts/:id/balance`) deliberately doesn't overwrite a stored number — it diffs the entered target against `list_accounts`' live hledger-computed balance and posts a dated adjustment transaction offset against `equity:adjustments` (`journal_writer::format_adjustment_transaction`), the standard hledger reconciliation idiom; hledger stays the sole source of truth and every correction leaves an auditable entry. `list_accounts` fetches every registered account's balance in one combined `hledger balance <path1> <path2> ... --flat -O json` call rather than one query per account. `finances::preview_projection` (`POST /api/v1/finances/projection/preview`, body `{items: PreviewItem[], exclude_recurring_ids: string[], months}`) lets the Recurring tab's chart preview a whole hypothetical scenario — any number of named, never-persisted extra recurring items (`PreviewItem`, add-only, one `~`-rule each) *and/or* one or more real recurring items excluded as if deleted — without touching the real journal or requiring a second round-trip per change. Rather than approximating the math client-side, it builds one scratch copy of the journal (real content, minus any blank-line-delimited block whose `id:` tag matches `exclude_recurring_ids`, plus one throwaway periodic rule per `PreviewItem`) at `<journal_path>.preview-<uuid>.tmp`, runs the normal `projection()` against that, then deletes the scratch file regardless of outcome; an entirely empty request (no items, nothing excluded) skips the scratch file and just re-runs the real projection. `exclude_recurring_ids` is never manually toggled anywhere — there is deliberately no "exclude this real item" button on the Recurring tab (an earlier eye-icon toggle doing exactly that was removed; it was disconnected from scenarios and easy to misuse into double-counting a payment a scenario was meant to replace). Instead, exclusion is always *derived*: a saved scenario item can optionally carry a `replaces_recurring_id` (see the Overview paragraph below), and only checked scenarios whose items set that field contribute to `exclude_recurring_ids` — a scenario item with no link never excludes anything, so nothing is ever excluded by accident. Either path overlays the result as a second, dashed "preview" dataset on the same Chart.js chart (`renderAcctChart`/`renderNetWorthChart`, see "Overview tab rebuild" below) rather than replacing the real one. Deleting a recurring item for real (`deleteRecurringItem`) still goes through a `confirm()`, but the message now names the item, its amount, and its frequency explicitly (rather than a generic "delete this?") and points at importing it into a saved scenario as the non-destructive alternative — the accidental-delete risk this addresses is specifically a recurring *expense* silently going unfunded because it was clicked away without a second thought. A `<input type="range">` (`fin-months-slider`, 1–36) controls how many months both the real and any active preview projection cover (`projectionMonths`, debounced via `scheduleMonthsRefresh` so dragging doesn't spam the API); the label above it (`fin-months-label`) stays in sync. The projection chart's `<canvas>` used to have no fixed-height container, so Chart.js's `maintainAspectRatio` (true by default) could size it tall enough to push the add-form/item-list out of view; it now sets an explicit `aspectRatio` computed from `window.innerWidth` (`chartAspectRatio` — tighter on narrow screens, wider on desktop) with `maintainAspectRatio: true`, re-picked on window resize, so height stays a bounded function of width instead of growing arbitrarily; `.finances-panel` also got its own `overflow-y: auto` override (the shared `.notes-panel, .log-panel, .todo-panel, .finances-panel` rule sets `overflow: hidden`) so the panel scrolls if the add-form + item list + preview builder + chart together still exceed the viewport — this only works, though, once *every* child actually participates in that one shared scroll region instead of carving out its own: both `.quick-note-form` and `.notes-list` normally claim `flex: 1` + their own `overflow-y: auto` (correct for Notes/Log/Todo, where a form or a list is a whole dedicated tab's *only* content), but Spending/Recurring/Accounts each stack form + list (+ preview + chart, for Recurring) together in one single panel — left unscoped, the form would claim the panel's leftover space and scroll *itself* in a squeezed box while the list/chart after it stayed fully, statically visible ("pinned") regardless of scroll position, the opposite of "let me see the form in full, the chart doesn't need to always be visible." `.finances-panel .quick-note-form` and `.finances-panel .notes-list` both override to `flex: none; overflow: visible` so every child folds into the panel's own normal document flow and the whole tab scrolls as one unit, top to bottom, chart included. Both the frontend (Finances → Accounts tab, plus an Account `<select>` on the Spending/Recurring add forms) and the TUI (`FinancesFocus::Accounts`, a third tab alongside Spending/Recurring, with its own add form and a `b` key on a selected account to open the balance-update prompt) expose accounts CRUD and the quick-balance-update action; the TUI's spending/recurring add forms cycle their Account field via Left/Right (`finances_cycle_account`, wrapping through `App.finances_accounts`) the same way Category/Kind/Frequency already cycled, rather than a free-text input. `Account` also carries an optional `interest_rate` (APR as a percentage) written as a trailing ` rate:{rate}` tag on the `account` directive — space-separated like `id:`/`name:`, but anchored from the *right* when parsing (`journal_parser::parse_account_block`'s `rfind(" rate:")`) since `name` is arbitrary free text that could itself contain the literal substring; this only works because the writer guarantees `rate:` is always the last tag appended. There was previously no way to edit an account's own fields at all (`set_account_balance` only ever posts a separate adjustment transaction) — `finances::update_account`/`journal_writer::rewrite_account` add a generic "delete the block, re-append with the same id" primitive (the same idiom `update_recurring_item`/`update_recurring_transfer`/`rewrite_recurring_item`/`rewrite_recurring_transfer` use to add editing to `RecurringItem`/`RecurringTransfer`, which previously had add/delete only), exposed as `PATCH /api/v1/finances/accounts/:id` and `PUT /api/v1/finances/recurring/:id`/`/recurring-transfers/:id`; the frontend's Recurring cards gained a pencil Edit button reusing the existing add form (`recurringEditingId`, mirroring Todo's edit-via-add-form convention), while Accounts' Edit stays a lightweight two-`prompt()` flow next to the existing balance-update prompt. `finances::debt_payoff_projection`/`PayoffPoint` is a second, deliberately separate projection — hledger's own `--forecast` posts a fixed $ amount per periodic rule and has no way to compute "X% of the current balance" each day, so true compounding interest can't be expressed as one more `~` rule for hledger itself to forecast; this is a from-scratch Rust calculation instead (`daily_rate = APR / 100 / 365`, applied to the balance carried in at the *start* of each day before that day's net scheduled recurring items/transfers against the account, the same convention a credit-card statement uses — issuers compound daily internally even though they only report a monthly total), exposed as `GET /api/v1/finances/accounts/:id/payoff?months=` (plain baseline) and `POST /api/v1/finances/accounts/:id/payoff/preview` (same, plus a budget-scenario overlay — see "Overview tab rebuild" below) and rendered as its own Chart.js line chart per liability account on the Overview tab (`renderOverviewAccountList`/`refreshAccountPanel`) — kept as its own math model, distinct from the plain linear forecast every asset account's own chart uses. `models::Frequency::occurrences_between` turns a recurring item/transfer's period expression into concrete occurrence dates (clamping day-of-month for monthly/yearly the same way a Jan 31 anchor lands on Feb 28, always computed from the original anchor day rather than an already-clamped previous step) — built for the payoff calculator, reused by recurring occurrence tracking below. `SpendingEntry` gained the same edit capability the other entities already had — `journal_writer::rewrite_spending_entry`/`finances::update_spending_entry` (the same delete-and-re-append-with-same-id idiom), exposed as `PUT /api/v1/finances/spending/:id` (id-mismatch checked the same way `update_todo_handler` already does); the frontend's Spending-tab cards gained a pencil Edit button (`spendingEditEntry`/`spendingResetForm`, mirroring the Recurring tab's `recurringEditingId` edit-via-add-form convention) that repopulates the Expense fields and switches `submitSpendingEntry`'s POST to a PUT — edit is expense-only, since one-off transfers have no update function or route (only add/delete).

**Spending-date exclusive-end-date bug**: `list_spending_entries`/`spending_stats`/`list_transfer_entries` all shell out with `-b <from> -e <to>`, and hledger's own `-e/--end` is *exclusive* (confirmed against a real `hledger` install: `-e 2026-07-28` returns zero transactions for an entry dated exactly `2026-07-28`) — but every caller's own `to` parameter is meant to be inclusive (e.g. the API layer defaults `to` to `Local::now().date_naive()` expecting "through today"). Previously unhandled, this meant an expense/transfer entered *today* silently vanished from the Spending tab's list and its category totals until the next calendar day, reappearing only once `to` had moved past it — easy to mistake for "the entry didn't save." Fixed with one private `end_exclusive(to: NaiveDate) -> String` helper (`finances/src/lib.rs`) that formats `to + 1 day` for the `-e` flag, used by all three functions; covered by a smoke-test case that lists with `to` set to an entry's own exact date and asserts it's still returned.

**Recurring occurrence tracking**: `RecurringItem`/`RecurringTransfer` are periodic *rules*, not individual billing occurrences, so a per-period "paid" tick needed a wholly new storage layer — the first SQLite table `finances`-adjacent data has ever needed, added to `db` rather than as a `finances` dependency on `db` (or vice versa), since `finances` is deliberately hledger-only and this tracking is explicitly not real ledger data: `recurring_occurrence_status` (`db::init`, keyed `(recurring_id, kind, period_start)`) stores only whether a given occurrence has been resolved — a missing row means "unresolved" (potentially overdue), a row with `paid = 0` means "explicitly marked not paid," resolved either way. The join between the two — `finances::list_recurring_items`/`list_recurring_transfers` for the schedule, `db::recurring_occurrence_get_all` for resolved state, `Frequency::occurrences_between` for the actual dates — lives in a new `app::finances_occurrences` module (`app` already depends on both crates directly, the same role `project` plays merging `lists`/`notes`/`todo`/`db`), computing each item's `current_period` (the most recent occurrence in a 12-month lookback window) and `outstanding` (every unresolved occurrence in that window, oldest first). `GET /api/v1/finances/recurring/occurrences?as_of=` is the frontend's one bulk fetch for every card's tick/badge (avoiding an N+1 fetch per card); `GET`/`POST /api/v1/finances/recurring/:id/occurrences?kind=` read/write a single item's occurrences, the POST body a list of `{period_start, paid}` upserts resolved in one call. Deleting a recurring item/transfer now also best-effort deletes its tracking rows (`db::recurring_occurrence_delete_for`) so they don't orphan. The frontend shows a checkbox tick per recurring card reflecting `current_period.paid` and, when any occurrence is overdue, a badge reusing `.note-badge.overdue` verbatim (previously only used on Todo due-date badges) — ticking an item with only the current period outstanding toggles it directly, but ticking one with multiple missed periods opens a new modal (`#occurrence-modal-backdrop`, this file's first actual centered dialog-with-backdrop component — everything else here is a native `confirm()`/`prompt()`, a full-screen `.app-overlay` section, or a small anchored `.cat-menu-dropdown` popover) listing every outstanding period with its own Paid/Not Paid radio, saved as one bulk `POST`.

**Finances Overview tab & budget system** — a 4th Finances tab consolidating everything "what does my financial future look like" into one page, rebuilt from scratch once (see "Overview tab rebuild" below for why) around exactly two chart concepts: a **Net Worth** chart (one line, every account summed) and one chart per **account** (asset and liability, always shown, never opt-in) — plus named, saved budget scenarios (the one remaining preview mechanism) and per-category spending caps layered on top. A budget scenario is a durable, reusable set of hypothetical income/expense items, stored in three `db` tables (`budget_scenarios`, `budget_scenario_items`, `budget_cap_allocations`), following the exact same "local metadata, not real ledger data, so it belongs in `db` not `finances`" reasoning already established for `recurring_occurrence_status`. `app::finances_budget` (mirroring `app::finances_occurrences`'s bridging role) provides thin CRUD wrappers over those tables plus `scenario_ids_to_preview_items`, which converts saved scenario items into `finances::models::PreviewItem`s (parsing `kind`/`frequency` back from plain strings via `serde_json::from_value`, since both enums are already `#[serde(rename_all = "lowercase")]`) for feeding into the real projection math — routes: `GET`/`POST /api/v1/finances/budget/scenarios`, `DELETE .../scenarios/:id`, `GET`/`POST .../scenarios/:id/items`, `DELETE .../scenarios/:id/items/:item_id`, `GET`/`POST /budget/cap-allocations`, `PUT`/`DELETE .../cap-allocations/:id` (see the budget-caps paragraph below for why this is a one-to-many allocations table rather than one row per category). The payoff side of this needed its own overlay mechanism: `finances::debt_payoff_projection` never actually calls hledger's forecast engine for its schedule (it already loops over `list_recurring_items`/`list_recurring_transfers` in plain Rust, only using `list_accounts` for the live starting balance/rate), so unlike `preview_projection`'s scratch-journal-file trick, a scenario overlay here needs no scratch file at all — `debt_payoff_projection_with_overrides(journal_path, account_id, months_ahead, extra_items, exclude_recurring_ids)` just filters/extends the same in-memory `Vec`s, and `debt_payoff_projection` is now a one-line wrapper calling it with empty slices; exposed as `POST /api/v1/finances/accounts/:id/payoff/preview`. Frontend: `financesOverviewOnOpen()` (hooked into `financesShowTab('overview')` and `financesOnOpen()`'s active-panel restore) loads saved scenarios, budget caps, and the per-account list; `collectPreviewItems()` flattens every checked (`appliedScenarioIds`) scenario's items and every budget-cap allocation marked "Include in projection" into one array plus a derived `excludeRecurringIds` set — the exact same `{items, exclude_recurring_ids}` shape is passed to *every* account's own preview fetch, so a scenario item posting against one specific account only ever moves that account's own line (and Net Worth, via the sum), never anyone else's.

A saved scenario item can carry an optional `replaces_recurring_id` (`budget_scenario_items.replaces_recurring_id`, nullable) — when set, applying that item's (checked) scenario adds the referenced real recurring item/transfer's id to `excludeRecurringIds`, so the edited replacement is the only one counted, never both (no stacking). `importRecurringToScenario` stamps every copy it creates with `replaces_recurring_id: item.id` automatically — an imported copy, edited or not, represents "this same payment, reconsidered," so excluding the original is always correct, even before any editing happens. The manual add-item form (`renderScenarioCard`) exposes the same link as a "Replaces" `<select>` (real items + transfers, default "— New payment —" / `null`), so a hand-typed item can optionally be linked too; an unlinked item is presumed genuinely new and never excludes anything. `replacingScenarioName(itemId)` is a pure display lookup (no exclusion logic of its own) that shows a small note on a Recurring-tab card when an applied scenario is currently standing in for it ("Replaced by scenario '…' in Overview"). Scenario items are editable in place — `db::budget_scenario_item_update` is a plain SQL `UPDATE` by id (unlike every `finances`-crate entity's delete-and-re-append-with-same-id idiom, a scenario item is just a regular table row, no journal file involved), exposed as `PUT /api/v1/finances/budget/scenarios/:id/items/:item_id`; the frontend's per-item pencil Edit button (`editScenarioItem`/`cancelScenarioItemEdit`) repopulates the same inline add-item form (including the "Replaces" link) and switches its submit from POST to PUT, the same single-form edit-in-place convention `recurringEditingId`/`spendingEditingId` already use elsewhere.

Budget caps (`db::budget_cap_allocations`) are otherwise a separate, unrelated-in-storage concept sharing this tab only because both feed "financial overview" — and, unlike scenarios, allow more than one account per category: a spending category's (stupid/survival) overall cap isn't stored directly, it's **derived** as the sum of that category's `budget_cap_allocations` rows (`id`, `category`, `account`, `amount`, `include_in_projection`), so a $1000 "stupid" budget can be split e.g. $600 on a credit account and $400 on checking with no risk of a stored total drifting out of sync with its parts. The derived total is compared against `loadSpendingStats()`'s already-fetched actual totals (`lastSpendingTotals`, no separate fetch) and flagged with the existing `.note-badge.overdue` token when exceeded. Each allocation carries its **own** "Include in projection" toggle, independent of its siblings in the same category — checking one folds just that allocation into `collectPreviewItems()`'s pool as an ongoing monthly expense against its own account, same as any scenario item; off by default, so adding an allocation alone never changes anything else. `app::finances_budget::add_cap_allocation`/`update_cap_allocation`/`delete_cap_allocation`/`list_cap_allocations` are thin CRUD wrappers (`update_cap_allocation` is a plain SQL `UPDATE` by id, same idiom `budget_scenario_item_update` established — `category` itself is never edited in place, moving an allocation to a different category is a delete + a new add) — routes: `GET`/`POST /api/v1/finances/budget/cap-allocations`, `PUT`/`DELETE .../cap-allocations/:id`. The frontend groups the flat `budgetCapAllocations` array client-side by category, rendering each category's derived total/actual-spend line above a list of its allocations (account, amount, its own checkbox, inline edit/delete — the same `editScenarioItem`-style convention) and a small per-category add-allocation form.

**Debt payment plans (removed from the frontend)**: a per-liability "Use payment plan" toggle (interest-only minimum + flat supplementary, replacing real recurring items for that one chart) used to exist alongside real recurring items as a second, competing way to model "what pays this debt down" — removed in the Overview rebuild (see "Overview tab rebuild" below) once a liability's minimum payment became always-real (a persisted recurring transfer) and "extra" became scenario-driven, since keeping both was part of the confusion. The backing Rust (`finances::debt_payoff_projection_with_plan`, `POST /api/v1/finances/accounts/:id/payoff/plan`) and its `compound_period`/`occurrence_date_set` machinery were left in place (a valid, tested API endpoint, just currently unused by this page) rather than deleted — no other consumer, but no reason to break the route either.

**Per-account plain-forecast math**: `finances::projection`/`preview_projection` were always just the same hledger-forecast math (`--historical --forecast`) hardcoded to the combined `["assets", "liabilities"]` account-path list — generalized by extracting that into two private helpers, `balance_forecast(journal_path, account_paths: &[&str], months_ahead)` and `balance_forecast_preview(journal_path, account_paths, months_ahead, items, exclude_recurring_ids)` (identical bodies to the originals, just parameterized), with `projection`/`preview_projection` becoming one-line wrappers calling them with `&["assets", "liabilities"]` — zero change to either function's public signature or existing callers/tests. `account_balance_history(journal_path, account_path: &str, months_ahead)` and `account_balance_history_preview(...)` are scoped to a single account's own `hledger_account()` path — deliberately the *plain* linear hledger forecast, not the interest-aware Rust math `debt_payoff_projection` uses for liabilities; every asset account's own chart on the Overview tab (see "Overview tab rebuild" below) reads these, while every liability account's own chart reads `debt_payoff_projection`/`_with_overrides` instead. Routes mirror the payoff pair exactly, named "history" to stay distinct from the pre-existing single-value `PATCH /accounts/:id/balance` quick-update: `GET /api/v1/finances/accounts/:id/history?months=`, `POST .../accounts/:id/history/preview` (reuses `PayoffPreviewBody`'s shape verbatim — `months`, `extra_items`, `exclude_recurring_ids` — rather than a near-duplicate struct); both handlers resolve `:id` to an `Account` via `list_accounts` first (404 on no match) before calling into `finances` with its resolved `hledger_account()` path, the same lookup-then-delegate shape `account_payoff_handler` already uses. `projection`/`preview_projection` themselves (and their `/projection`, `/projection/preview` routes) are no longer called by any frontend page as of the Overview rebuild — Net Worth is computed client-side instead (see below) — but stay as valid, tested public API, not deleted.

**Chart legend/colors/breakdown**: every chart always shows a Chart.js legend with a consistent color convention — blue/teal for the real baseline, dashed amber for the "preview" line, thin grey dotted for the trendline — and each has a plain-text breakdown underneath that's *always populated*, not just shown when something unusual is active: `renderNetWorthBreakdown()` always states "Solid = every account's real baseline added together..." and switches to a "Dashed = ... scenarios applied..." wording once any account actually has a preview; `renderAcctBreakdown()` (every account card, asset or liability) always states what that account's solid line is built from — a liability's interest rate plus exactly which real recurring items/transfers are scheduled against it (via the shared `scheduledSummaryText()`/`scheduledAgainstAccount()` helpers — transfers count here too, into an account pays it down, out of it makes it worse, not just expense/income items), an asset's real transactions plus its own scheduled items/transfers — then a "Dashed = ..." line only when that specific account has a preview. The goal throughout is that "what's contributing to this chart" is answerable by reading the card, never by inferring it from which controls happen to be checked — these breakdown `<div>`s are plain `.field-label`s, not gated behind the Overview tab's collapsible `.overview-help` blurbs, so they're visible without opening Help. Every account's own chart (`renderAcctChart`, one function for both kinds — `accountValueField(kind)` picks `'ending_balance'` vs `'balance'`) always fetches the plain baseline *and*, only when that account actually has a preview, a second series; the Net Worth chart is the client-side sum of whichever of those two each account currently has. Every chart is driven by the same `projectionMonths` global set by the one months slider in the "Net Worth" section — `scheduleMonthsRefresh()` re-fetches everything together on drag, so nothing ever shows a different window than any other chart; only the fixed-`SUMMARY_MONTHS=120` checkpoint tiles are deliberately independent of the slider (see "Checkpoint summaries" below).

**Recurring items: budget category attribution, and transfers already counting toward payoff**: `RecurringItem` gained an optional `category: Option<SpendingCategory>` (`finances/src/models.rs`) — purely bookkeeping metadata layered on top of the item's existing `expenses:{label}` posting account (unchanged; a recurring item still gets its own named ledger sub-account, e.g. `expenses:netflix`, not `expenses:stupid` directly), written as a trailing ` category:{tag}` tag on the `~`-rule header (`journal_writer::format_recurring_item`, `SpendingCategory::tag()`/`from_tag()`) using the same right-anchored trailing-tag parsing idiom as the account directive's `rate:`/`limit:` (see below) — `journal_parser::parse_block` strips it via `rfind(" category:")` before extracting `name`. Exposed as an optional `category` field on `AddRecurringBody`/`UpdateRecurringBody`, and on the frontend as a "Budget Category" `<select>` on the Recurring tab's add/edit form (shown only for Kind=Expense — income items don't have one). Since periodic rules only ever appear in a projection via hledger's own `--forecast`, a category-tagged recurring item still never shows up in `spending_stats`' real-transaction totals; instead, the Overview tab's Budget Caps section now shows a second figure per category — `recurringMonthlyCommitment()` sums every category-tagged expense item's amount normalized to a monthly equivalent (reusing the Recurring tab's own `MONTHLY_FACTOR`) and displays it as "+ $X/mo recurring" alongside the real actual-spend total, both compared against the category's derived cap. Separately: a recurring *transfer* into a liability account already paid it down (and one out of it already made it worse) in `debt_payoff_projection`'s own math well before this — `net_scheduled_amount` in `debt_payoff_projection_with_overrides` already loops `list_recurring_transfers` alongside `list_recurring_items`, adding `+transfer.amount` when `to_account` matches and `-transfer.amount` when `from_account` does (covered by the existing `debt_payoff_projection_stops_early_once_paid_off` test) — this was already correct but not visible in the UI, so each liability's own card breakdown (`renderAcctBreakdown`, via the `scheduledAgainstAccount()` helper) explicitly lists every real recurring item *and* recurring transfer currently scheduled against that account (name, amount, frequency, direction), so a transfer's contribution is confirmable at a glance instead of taken on faith; the Overview tab's "Accounts" help blurb states the same thing in prose.

**Account credit limits**: `Account` gained an optional `credit_limit: Option<f64>` (display/utilization metadata only — never enforced, never fed into any projection or payoff math), written as a second trailing tag on the `account` directive, after `rate:` when both are present (`format_account_directive`'s header-building now appends `rate:`, then `limit:`, in that fixed order). Parsing mirrors the existing `rate:` idiom but has to peel two optional trailing tags off `name` instead of one — `journal_parser::parse_account_block` strips `" limit:"` first via `rfind` (since it's always the outermost/last-appended tag when present), then `" rate:"` from what remains, so a name containing either literal substring (or both) still parses correctly regardless of which real tags are present. `create_account`/`update_account` and their API bodies/routes thread the new parameter through the same way `interest_rate` already does. The frontend's Accounts tab shows a "Credit Limit" input alongside "Interest Rate" (both liability-only, toggled by `updateAccountKindFields`) and, on each liability card, a used/limit/percentage line (`$used / $limit (NN%)`, used = `max(0, -balance)`) with a `.note-badge.overdue`-styled "Near Limit" badge once utilization crosses 90%.

**Checkpoint summaries**: a fixed `SUMMARY_MONTHS = 120` fetch (independent of the interactive chart's own `projectionMonths`, which stays capped at 36 for chart readability) reads off balances at `[12, 24, 36, 60, 120]` months — `refreshAccountPanel`'s own 120-month `fetchAccountPair` call, per account, cached into `lastAccountPoints[id].summary`, then `computeNetWorth('summary')` sums those for the Net Worth tiles the same way `computeNetWorth('chart')` sums the interactive-depth series — rendered as small stat tiles (`renderCheckpointSummary`). Since points are daily (see below), a checkpoint can't be picked by array index (`points[monthIdx - 1]`, the old scheme) — `renderCheckpointSummary`'s `cellHtml` instead computes a target calendar date (`points[0].period_start` plus N months via `Date.setMonth`) and scans for the last point whose `period_end` doesn't exceed it. A liability array can end early (paid off); any checkpoint past its last date shows the payoff date instead of a raw balance, while an asset's (or Net Worth's) array, which never stops early on its own, just shows its last real value in the rare case hledger returns fewer points than requested (an empty-journal edge case, not a payoff concept). This is 1-2 extra requests per account per refresh, an accepted tradeoff for simplicity over minimizing requests, consistent with this codebase's existing "recompute the full set" preference elsewhere (e.g. `finances_occurrences::compute_occurrences_for`).

**Daily balance/payoff granularity**: every finances chart used to plot one point per *month*; all now plot one point per *day*. For the hledger-backed charts (`balance_forecast`/`balance_forecast_preview` — i.e. `projection`, `preview_projection`, `account_balance_history`, `account_balance_history_preview`), this was a one-line change (`-M` → `-D` on the `hledger balance` call, confirmed against a real `hledger` install to return the identical `prDates`/`prTotals` JSON shape either way) — the real ending balances are unchanged, hledger just reports them at finer intervals. The custom Rust payoff math (`debt_payoff_projection_with_overrides`/`_with_plan`) needed an actual rewrite: the loop now steps one calendar day at a time (`daily_rate = APR/100/365` instead of `monthly_rate = APR/100/12`, applied via the renamed `compound_period` — previously `compound_month`, whose body was already period-agnostic) rather than one calendar month. Naively shrinking the old per-period `occurrences_between(ref, period_start, period_end)` call to a per-day `[day, day]` window would have been wrong, though — `occurrences_between`'s `None`-reference-date fallback anchors at the window's own `start`, so a fresh `[day, day]` window every iteration would make a reference-date-less item fire on literally every day instead of respecting its real frequency (the old monthly loop "got away" with this only because a whole month is wide enough to contain that frequency's real cadence). Fixed by `occurrence_date_set(frequency, reference_date, start, end)`, which computes each item's/transfer's exact occurrence dates *once* over the whole horizon with one stable anchor, returned as a `HashSet<NaiveDate>` the daily loop then just checks membership against per day — same fix applied to the plan's `supplementary_frequency`. Existing payoff tests that asserted an exact `points.len()` (one per month) were rewritten to compute the expected day count via `models::add_months_clamped` instead. `finances_occurrences`' recurring-occurrence-tracking module (paid/overdue ticks) is unrelated to any of this — it already worked in real calendar dates via the same `Frequency::occurrences_between`, never through these monthly/daily chart points.

**Combined/account-balance chart bug: missing `-b` let the whole ledger history leak in**: `balance_forecast` passed `--historical` (which folds everything *before* the report's begin date into the first period's starting balance) but never actually passed a `-b` (begin date) to go with it — so hledger's report began at the journal's *very first* transaction, not "today," on every call. On a journal with any real history this meant every daily/weekly point *already elapsed* since the account was created got returned on top of the `months_ahead` window actually asked for (confirmed against a real `hledger` install: a journal with ~7 months of history and a 1-month-ahead request returned 205 points instead of ~31) — the combined chart, both payoff-adjacent per-account balance charts, and every downstream calc keyed off `points[0].period_start` (the trendline's x-index-vs-value regression is unaffected since it's index-based, but `renderCheckpointSummary`'s "N months from `points[0].period_start`" target-date math silently anchored to account-creation day instead of today) were all quietly showing months or years more data than the slider claimed, with no visual marker distinguishing "already happened" from "forecast" — easy to misread as duplicated or inflated spending. Fixed by passing `-b <today>` alongside the existing `--historical`, which is exactly the flag that makes this safe (prior real balance is folded in, not lost) — `projection_excludes_history_before_today_from_point_count` (a journal seeded with a transaction 200 days back, asserting the 1-month-ahead point count and `points[0].period_start` both land on today) locks this in. This was a real, confirmed correctness bug, not a duplication in the sense of the same transaction posting twice — no double-entry/double-counting bug was found in `collectPreviewItems()` or the exclude-recurring-id mechanism on review.

Daily granularity alone would put 3650+ points on a 10-year chart, so every one of these functions steps back down to *weekly* once `months_ahead` exceeds 12: `balance_forecast` swaps hledger's `-D` for `-W` (same JSON shape, confirmed against a real install) at that threshold, and the payoff loops fold `payoff_step_days(months_ahead)` (1 or 7) consecutive daily steps into one emitted `PayoffPoint` via a small `PayoffBucketer` accumulator — every day is still compounded individually and in order (interest/scheduled amounts within a bucket are exact sums, not a 7-days-at-once approximation), only the *emitted* points are coarser; a bucket flushes early (partial, never silently dropped or padded) the moment the account is paid off or the horizon ends mid-bucket. Covered by `debt_payoff_projection_switches_to_weekly_buckets_beyond_12_months` (18-month horizon, asserts weekly point count and that no bucket exceeds 7 days).

**Chart trendlines**: every finances chart (`renderNetWorthChart`, `renderAcctChart`) also plots a `trendlineDataset()` — a least-squares linear regression line (`linearTrendline()`) over the baseline series only (never the preview series), styled as a thin muted-grey dotted line so it reads as a background reference rather than competing with the established blue-baseline/amber-preview convention. Regressed against each point's *array index*, not its calendar date — points aren't evenly spaced in time once weekly bucketing kicks in past 12 months, but they're always evenly spaced by index, which is all a straight trendline needs (and keeps the same function correct for both daily- and weekly-spaced series without needing to know which).

**Transfers between accounts** (`TransferEntry`/`RecurringTransfer`, `/api/v1/finances/transfers` and `/api/v1/finances/recurring-transfers`) — moving money between two of the user's own accounts, both one-off and recurring, added into the existing Spending and Recurring tabs rather than as a separate screen (an "Expense"/"Transfer" pill toggle in Spending swaps the category+account fields for from/to-account fields; a third "Transfer" option on Recurring's Kind select does the same). Structurally neither leg is an `expenses:`/`income:` category — both are real accounts — so neither fits the existing `SpendingEntry`/`RecurringItem` shapes or their parsers, which both hinge on exactly one leg being a category account; transfers get their own dedicated writer/parser functions instead of overloading those. `format_transfer_entry` writes `to_account` with the explicit `$amount` and leaves `from_account`'s implicit (hledger auto-balances it to the negative) — same one-posting-explicit convention as every other two-line entry here — tagged `; id:{id}, transfer:1` in the comment. That tag is **comma**-separated, unlike the **space**-separated `id:{id} name:{name}` convention `RecurringItem`/`RecurringTransfer` use elsewhere in this module — confirmed empirically against a real `hledger` install that its own tag parser only splits comment tags on commas, so a space-separated `id:x transfer:1` parses as a single `id` tag whose value is the literal string `"x transfer:1"`, not two tags. The comma matters here specifically because one-off transfers are real transactions queried back out via hledger's own `tag:transfer` search (`list_transfer_entries`, mirroring `list_spending_entries`'s `print ... -O json` pattern) rather than parsed from local file text — to_account/from_account are told apart by amount sign (positive = to, negative = from) once hledger resolves both postings' amounts. `RecurringTransfer` (a periodic rule) stays on the local-file-parsing path `RecurringItem` already uses (periodic rules aren't real transactions hledger can query), so its own `id:`/`name:` tags stay space-separated for consistency with that convention; `journal_parser::parse_recurring_transfers` filters for `~`-blocks containing `transfer:1`, and the ordinary `parse_recurring_items` pass naturally (harmlessly) rejects those same blocks since neither leg is `expenses:`/`income:`-prefixed — confirmed via tests in both directions (a transfer block never parses as a regular item and vice versa). A transfer between two asset accounts (or two liability accounts) has no net effect on `projection()`'s combined assets-liabilities trend, correctly, since it's purely internal movement — verified via the real-hledger smoke test. Deleting either kind reuses the existing generic `remove_block_with_id`; excluding a recurring transfer from a projection preview (see below) already works for free, since `exclude_recurring_ids` matches by `id:` tag regardless of block type. The frontend merges both entities into their host tab's existing list (`_type: 'expense'|'transfer'` / `_type: 'regular'|'transfer'` tags added client-side after fetching each in parallel), so delete/preview-removal-toggle route to the right endpoint per item without a separate UI section.

**Project Detail return-navigation, round two**: the above fixed every *exit point that already had* `pendingProjectReturnId`/`extra.projectId` handling, but missed three more gaps in the same family, plus a genuinely separate stale-fetch race that turned out to be the actual cause of the "swipe/back from Notes shows a blank Project Detail" reports — confirmed root cause only after the navigation-mechanism itself was proven correct via faithful headless replay (a real DOM, the real inline script, a real backend, including the user's own live "manage_dan" project data) and still reproduced. `submitQuickNote()` (creating a note) never checked `pendingProjectReturnId` at all, unlike `submitLogEntry`/`submitTodo` — fixed to match: on success it now returns to Project Detail when set, instead of always landing on the plain unscoped Notes Browse tab. `openProjectListCategory()` (Project Detail's Lists section → a category) called `showView('lists')` with no `extra` at all — the one project-exit call site with zero threading — fixed to thread `{projectId: currentProjectDetailId}` like every other one; deliberately does *not* also set `pendingProjectReturnId`, since Lists has no submit/cancel workflow to consume it on exit, and leaving it set would leak into whichever unrelated Notes/Todo/Log save happens next and wrongly redirect *that* back to this project. `notesOpenNote()` (opening a specific note) also called `showView('notes')` with no `extra`; fixed for consistency, though it's a no-op for the common case since `showView`'s own `changed` guard already skips the history push once `currentView` is already `'notes'`. **Overview tab rebuild — Net Worth + one chart per account**: the Overview tab accumulated three separate, overlapping ways to answer "what pays this debt down" across several rounds (a combined chart, per-liability "Debt Payoff Projections" cards with their own ephemeral "Use payment plan" toggle, and an opt-in "Account Balances" checklist) — confusing enough that it was rebuilt from scratch rather than patched again. This whole page needed zero new backend code — every data source already existed; the only genuinely new logic was this client-side summing, per the "use what's already there, add logic only where hledger truly can't help" approach taken for the rebuild.

**Notes: choose a folder at create time**: `notes::create`'s `CreateNoteRequest` gained an optional `folder` field — previously a freshly-created note always landed at its notebook's root, with moving into a subfolder only possible as a separate, later "Move" action. The underlying `nb add` command has no folder-targeting flag at all, so this is implemented as create-then-move under the hood: `notes::create` still creates at root first, then, if a non-empty `folder` was requested, best-effort creates the destination folder (`nb_client::nb_add_folder`, already idempotent/error-ignoring — the same call the notes-tree "Move" action's "+ New folder" flow uses) and immediately moves the freshly-created note into it (`nb_client::nb_move`), caching only the note's final resolved location rather than caching the transient root placement first. The frontend's note-create form gained a plain free-text "Folder" input (e.g. `Projects/Sub`) alongside the existing free-text Notebook field, deliberately not the notes-tree "Move" action's live folder-picker-menu convention — that menu requires fetching an existing notebook's folder tree, which doesn't work cleanly when the Notebook field itself might name a notebook that doesn't exist yet (a new notebook being created in the same request).

**Deployment**: dev and prod are the same machine — no Docker, no cross-compilation. `deploy.sh` builds `app` natively (`cargo build --release -p app`), installs it to `/usr/local/bin/manage_dan`, and installs/restarts a `manage_dan` systemd unit (`WorkingDirectory` = project root, so relative paths like `app.sqlite` and `data/logs/app.log` resolve the same as under `cargo run`) plus an nginx reverse proxy (serves `frontend/index.html`, proxies `/api/`, `/todo/`, `/notes/`, and `/list/` to `127.0.0.1:8080` — every top-level QR-linked page's path prefix needs its own `location` block here, since nginx's default `location /` only serves the SPA's static `index.html`). See the script's header comments for one-time setup (nginx, `nb`, `zip` for project archiving, `plugdev` group for USB printer access). For frontend-only changes (no backend/API/schema change), `deploy-frontend.sh` just re-copies `frontend/index.html` to the nginx static path — no rebuild, no service restart, so the running app's in-memory/monitor state is undisturbed.
